# msgserv

## Описание

`msgserv` — системный сервис обмена сообщениями между нативными приложениями
PUNos. Он опознаёт подключившееся приложение по выданному `appserv` токену,
ведёт подписки на topic'и, доставляет опубликованные события всем подписчикам
и маршрутизирует адресные запросы с ответом между экземплярами приложений.

Для `msgserv` payload сообщения непрозрачен. Сервис не знает, на каком языке
написано приложение, не интерпретирует содержимое сообщений и не зависит от
внутреннего runtime приложения.

## Имя сервиса

| Поле | Значение |
| --- | --- |
| Идентификатор | `msgserv` |
| Исполняемый файл | `msgserv` |
| Владелец запуска | `initserv` |
| IPC endpoint | `/run/punos/msgserv.sock` |
| Версия протокола | v1 |

## Ответственность и границы

- `msgserv` хранит статический каталог `MessagingSpec`, сгенерированный при
  сборке из `PlatformRegistry`, и общий `PlatformRegistryId`.
- `msgserv` принимает одно control-соединение от `appserv`, опознанное
  `MsgControlToken`, и ведёт по нему таблицу живых экземпляров приложений.
- `msgserv` опознаёт каждое клиентское соединение по `MessagingToken` и
  связывает его с парой (`application_id`, `instance_id`).
- `msgserv` ведёт подписки на topic'и и доставляет событие каждому подписчику,
  которому разрешено его получать.
- `msgserv` выдаёт `correlation_id` адресным запросам, доставляет их адресату,
  возвращает ответ отправителю и закрывает запрос по дедлайну.
- `msgserv` ограничивает собственную очередь каждого получателя и отбрасывает
  события при её переполнении, сообщая об этом отправителю.
- `msgserv` не создаёт процессы, не хранит `ProcessHandle` и не запускает ELF:
  это делает `appserv`.
- `msgserv` не управляет системными сервисами: их запускает и перезапускает
  `initserv`.
- `msgserv` не сохраняет сообщения на диск, не гарантирует доставку и не
  повторяет попытки.
- `msgserv` не является посредником между приложением и `logserv`, `IOserv`,
  `camserv`, `locationserv` или UI-серверами.
- `msgserv` не выдаёт и не изменяет права во время работы: каталог прав
  неизменен в пределах запуска сервиса.
- `msgserv` не интерпретирует payload приложения и не знает его формата.

## Зависимости

| Зависимость | Использование |
| --- | --- |
| `sys/core` | `ErrorCode`, базовые типы, `Bytes` и проверка размеров payload |
| `sys/memory` | Клиенты, подписки, очереди, pending-запросы и ответы |
| `sys/string` | `application_id`, `topic`, `method` и IPC endpoint в UTF-8 |
| `sys/eventloop` | Один event loop для endpoint, соединений и таймера дедлайнов |
| `sys/time` | `DurationMs` для дедлайнов запросов и bind |
| `special/ipc` | Endpoint, соединения, кадрирование и исходящие очереди |
| `logserv` | Журналирование отказов, отбрасываний и жизненного цикла клиентов |
| `special/log` | Только константы и значения `LogSeverity` для совместимости с протоколом `logserv`; линковка не требуется |

`MessagingSpec` генерируется при сборке из `MessagingLaunchSpec` статического
`PlatformRegistry` `initserv`. Сборка требует точного совпадения
`application_id` с каталогом `NativeAppSpec` и встраивает общий
`PlatformRegistryId`. Поэтому `msgserv` получает уже разрешённый каталог прав
и не проверяет во время работы реестр, которого не видит.

`msgserv` не зависит от `appserv` при сборке и не является его клиентом:
направление control-соединения обратное — подключается `appserv`.

## Жизненный цикл

### Запуск

| Параметр | Значение |
| --- | --- |
| Готовые сервисы до запуска | `logserv` |
| Успех | Проверены `PlatformRegistryId` и каждый `MessagingSpec`; получен `MsgControlToken`; созданы event loop, endpoint и таймер дедлайнов |
| Ошибка каталога или инициализации | Endpoint не создаётся; завершение с `PROCESS_EXIT_INITIALIZATION_FAILED` (3) |

`msgserv` не имеет клиентов при собственном старте и переходит в `Ready`.
Endpoint создаётся **последним** шагом инициализации: по контракту `logserv`
endpoint появляется только после подтверждённой готовности, и `msgserv`
повторяет это правило — наличие `/run/punos/msgserv.sock` означает, что сервис
готов принимать bind.

### Остановка и восстановление

При переходе в `Stopping` сервис прекращает приём новых соединений, запрещает
`publish`, `subscribe` и `request`. Каждому клиенту с незакрытым
pending-запросом отправляется `deliver_response` с `CORE_INVALID_STATE`, после
чего выполняется `ipc_connection_flush()` и `ipc_connection_close()` для
каждого соединения, затем закрываются endpoint и event loop.

Сообщения не сохраняются. При аварийном завершении `msgserv` `initserv` может
перезапустить сервис, но все подписки, pending-запросы и таблица экземпляров
теряются. Приложения обнаруживают это как `PeerClosed` на своём соединении и
обязаны выполнить bind и подписки заново; `appserv` обязан переоткрыть
control-соединение и перерегистрировать живые экземпляры.

Восстановление подписок — ответственность `appframework`, а не приложения:
см. [`appframework-messaging.md`](appframework-messaging.md#переподключение).

### Состояния сервиса

| Состояние | Допустимые действия | Переходы |
| --- | --- | --- |
| `Starting` | Проверка каталога, создание event loop, endpoint и таймера | `Ready`, `Failed` |
| `Ready` | Bind, подписки, публикация, запросы, ответы | `Stopping`, `Failed` |
| `Stopping` | Отмена pending-запросов, flush и освобождение ресурсов | `Stopped` |
| `Failed` | Новые операции не принимаются | Завершение процесса |

### Состояния клиентского соединения

| Состояние | Значение | Допустимые входящие сообщения |
| --- | --- | --- |
| `Unbound` | Соединение принято, личность не подтверждена | `bind`, `control.bind` |
| `Bound` | Личность подтверждена валидным токеном | `subscribe`, `unsubscribe`, `publish`, `request`, `respond` |
| `Control` | Control-соединение `appserv` | `control.instance_register`, `control.instance_release` |
| `Draining` | Сервис в `Stopping`, идёт слив исходящей очереди | нет |

Сообщение, не допустимое в текущем состоянии, получает ответ
`CORE_INVALID_STATE`. Соединение в `Unbound`, не выполнившее bind за
`MSG_BIND_TIMEOUT_MS`, закрывается без ответа.

## Владение ресурсами

| Ресурс | Владелец | Создание | Освобождение |
| --- | --- | --- | --- |
| `MessagingSpec[]` и `PlatformRegistryId` | `msgserv`, статический каталог | До запуска, встроен в образ | При завершении `msgserv` |
| `IpcServerHandle` | `msgserv` через `ipclib` | Последним шагом инициализации | При остановке |
| `IpcConnectionHandle` | `msgserv` через `ipclib` | При `accept` | При `PeerClosed`, отказе или остановке |
| `Client` (личность, подписки, очередь, счётчики) | `msgserv` | При `accept` | При закрытии соединения |
| Запись `InstanceTable` | `msgserv` | По `control.instance_register` от `appserv` | По `control.instance_release` либо при закрытии control-соединения |
| `Pending` (запрос в полёте) | `msgserv` | При `request` | При ответе, дедлайне либо отключении любой из сторон |
| Payload принятого кадра | `msgserv` до постановки в очередь | `ipc_connection_receive()` | `ipc_message_destroy()` ровно один раз |
| `EventLoopHandle` и таймер | `msgserv` | При запуске | При остановке |

`correlation_id` уникален, пока запрос существует в памяти `msgserv`. Он не
переиспользуется в рамках одного запуска сервиса. `instance_id` выдаёт
`appserv`, `msgserv` его не изобретает.

## Лимиты

| Константа | Значение | Обоснование |
| --- | --- | --- |
| `MSG_PROTOCOL_VERSION` | `1` | Как `APP_PROTOCOL_VERSION` |
| `MSG_TOKEN_SIZE` | `32` | Как `ShellToken` в GUI-слое |
| `MSG_TOPIC_MAX_LENGTH` | `128` | Длиннее `application_id`, короче пути endpoint'а |
| `MSG_METHOD_MAX_LENGTH` | `64` | Как `APP_TEXT_MAX_LENGTH` |
| `MSG_PAYLOAD_MAX_SIZE` | `65536` | 64 КиБ × 64 подписчика = 4 МиБ, то есть полный fan-out помещается в предел очереди `ipclib` одного соединения |
| `MSG_CLIENTS_MAX` | `64` | Как `APP_CATALOG_MAX_COUNT`: больше приложений в каталоге нет |
| `MSG_TOPICS_MAX` | `256` | Ограничивает `TopicTable` |
| `MSG_SUBSCRIPTIONS_MAX_PER_CLIENT` | `32` | Ограничивает работу на один `publish` |
| `MSG_SUBSCRIBERS_MAX_PER_TOPIC` | `64` | Равно `MSG_CLIENTS_MAX` |
| `MSG_QUEUE_MAX_RECORDS` | `1024` | Своя очередь получателя; у `logserv` 4096 при меньшем размере записи |
| `MSG_QUEUE_MAX_BYTES` | `1048576` | 1 МиБ — в четыре раза мягче `IPC_OUTGOING_QUEUE_MAX_SIZE`, чтобы отказ приходил от `msgserv`, а не из транспорта |
| `MSG_PENDING_MAX_PER_CLIENT` | `256` | Как `APP_APPS_MAX_PENDING` |
| `MSG_PENDING_MAX_TOTAL` | `4096` | Защита от исчерпания памяти суммой клиентов |
| `MSG_REQUEST_TIMEOUT_MS` | `30000` | Верхняя граница жизни pending-запроса |
| `MSG_BIND_TIMEOUT_MS` | `5000` | Как таймаут запуска `logserv` в `initserv` |
| `MSG_DEADLINE_TICK_MS` | `1000` | Как таймер `process_poll` в `appserv` и монитор `initserv` |

## Контракты

1. Все ошибки IPC-ответов являются `ErrorCode` из `libcore`; `CORE_OK` —
   единственный успешный код.
2. До создания endpoint `msgserv` проверяет `PlatformRegistryId`, уникальность
   `application_id` в каталоге прав, корректность UTF-8 каждого topic'а и
   метода и соблюдение всех лимитов каталога. Несовпадение с `PlatformRegistry`
   является ошибкой сборки; ошибочный встроенный каталог не запускает сервис.
3. Личность клиента определяется **только** валидным `MessagingToken` из
   `InstanceTable`. Никакое поле payload не влияет на то, кем считается
   отправитель. Поля отправителя в доставляемых кадрах заполняет `msgserv`.
4. Токен проверяется ровно один раз, при bind. После успешного bind токен в
   памяти клиента не хранится и не журналируется.
5. Права на `publish`, `subscribe`, вызов метода и его обслуживание берутся из
   `MessagingSpec` по `application_id` клиента. Отказ — `CORE_PERMISSION_DENIED`.
6. `CORE_OK` на `publish` означает постановку в очереди получателей, а не
   доставку и не сохранение. Доставка — at-most-once, повторов нет.
7. Переполнение очереди получателя отбрасывает кадр для этого получателя,
   увеличивает его `sequence` по этому topic'у и увеличивает `dropped_count`
   в `publish_result`. Остальные получатели этим не затрагиваются.
8. Переполнение собственных лимитов отправителя (`MSG_PENDING_MAX_PER_CLIENT`,
   `MSG_PENDING_MAX_TOTAL`) возвращает `CORE_WOULD_BLOCK`, как исчерпание
   очереди `logserv`.
9. `sequence` монотонен для пары (получатель, topic) в пределах одного
   соединения и увеличивается на единицу на каждое событие — доставленное или
   отброшенное. Разрыв означает потерю.
10. Каждый pending-запрос завершается ровно одним `deliver_response`:
    ответом адресата, дедлайном (`CORE_TIMEOUT`), отключением адресата
    (`CORE_NOT_FOUND`) либо остановкой сервиса (`CORE_INVALID_STATE`).
11. `respond` с неизвестным, уже закрытым или принадлежащим другому адресату
    `correlation_id` возвращает `CORE_NOT_FOUND` и не доставляется никому.
12. Закрытие соединения снимает все его подписки, отменяет все его
    pending-запросы в обе стороны и освобождает его очередь.
13. Все операции с соединениями, таблицами и очередями выполняются одним
    потоком-владельцем event loop.
14. Ни одна операция сервиса не блокирует поток: при `CORE_WOULD_BLOCK` от
    `ipclib` кадр остаётся в собственной очереди до `EVENT_WRITABLE`.
15. Payload приложения не журналируется ни при каких обстоятельствах. В
    журнал попадают `application_id`, `instance_id`, topic, метод, код ошибки
    и счётчики — но не содержимое сообщений.
16. `msgserv` корректно завершает процесс после `SIGTERM`: это обязательное
    условие каталога v1 для всех зарегистрированных сервисов, `initserv` не
    использует `SIGKILL` и таймауты завершения.

## Потоковая модель и асинхронность

`msgserv` v1 однопоточный. Один поток владеет event loop'ом, endpoint'ом,
всеми `IpcConnectionHandle`, каталогом `MessagingSpec` и всеми таблицами.

Таймер event loop с периодом `MSG_DEADLINE_TICK_MS` проверяет дедлайны
pending-запросов и соединений в `Unbound`. Проверка выполняется на владельце
даже если тик совпал с обработкой другого события, иначе дедлайн может быть
пропущен — та же проблема, которую `initserv` решает проверкой наступивших
дедлайнов на владельце.

Файловых операций у сервиса нет, поэтому отдельный worker-поток, как в
`logserv`, не нужен.

## Конфигурация и постоянные данные

| Данные | Источник | Владелец | Действие при ошибке |
| --- | --- | --- | --- |
| Каталог `MessagingSpec` и `PlatformRegistryId` | Сгенерированы при сборке из `PlatformRegistry` | `msgserv` | Несовпадение или некорректная запись запрещают запуск до создания endpoint'а |
| `MsgControlToken` | `initserv` при запуске, startup handoff | `msgserv` и `appserv` | Отсутствие токена — ошибка инициализации, выход с кодом 3 |
| Подписки, клиенты, pending-запросы | Память `msgserv` | `msgserv` | Теряются при перезапуске сервиса |

Установка прав во время работы, файл конфигурации, durable-очередь и история
сообщений в v1 отсутствуют.

## Логирование и наблюдаемость

После готовности `logserv` сервис записывает: запуск и остановку, bind и
отключение клиента (`application_id`, `instance_id`), отказ bind с причиной,
отказ по правам (`application_id`, topic или метод), отбрасывание события
(получатель, topic, число отброшенных), таймаут запроса, переполнение
pending-таблиц и любой отказ `ipclib`.

Уровни — `LogSeverity` из `loglib`: `INFO` для жизненного цикла клиентов,
`WARNING` для отбрасываний и таймаутов, `ERROR` для отказов `ipclib` и
нарушений протокола, `FATAL` перед аварийным завершением.

Технические диагностики используют ту же ограниченную очередь к `logserv`,
что и у других сервисов: при её переполнении диагностика откладывается до
появления места, а не теряет сервис.

## Границы v1

| Не входит в v1 | Почему |
| --- | --- |
| Персистентность и durability | `logserv` v1 тоже не даёт durability; очередь на диске требует своего формата и ротации |
| Доставка незапущенному адресату, launch-on-demand | Требует, чтобы `msgserv` стал клиентом `appserv`, и вводит цикл `msgserv → appserv → приложение → msgserv` с отложенной доставкой |
| Передача дескрипторов и разделяемой памяти | `SCM_RIGHTS` появляется в `ipclib` только в GUI-ветке; крупные данные в v1 передаются по 64 КиБ либо вне брокера |
| Wildcard-topic'и (`sensor.*`) | Усложняют проверку прав и `TopicTable` без доказанной потребности |
| Фильтры по содержимому | Нарушили бы контракт 15 — брокер не смотрит в payload |
| Приоритеты сообщений | Одна очередь на получателя — достаточное поведение при at-most-once |
| Опрос состава topic'а | Утечка информации о других приложениях; нужна отдельная модель прав |
| Сетевой транспорт | `ipclib` по контракту 1 только локальный, `AF_INET` не поддерживается |

Планы по каждому пункту — в [`roadmap.md`](roadmap.md#после-v1).
